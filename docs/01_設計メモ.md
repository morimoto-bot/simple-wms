## 1. ねらいと構成

商品マスタを持ち、iPhoneのバーコード読み取りで「入荷」「出荷」「検品」「棚卸し」ができ、在庫が動き、置き場所（ロケーション）も管理できる簡易WMS。

以前の失敗の原因は「画面をGASのWebアプリ（HtmlService）に載せたこと」。GASの画面はiframeの中で動くため、カメラ（getUserMedia）が使えない。今回は役割を分ける。

- 画面 = 単一HTML（HTTPSで配信。ブラウザ表示でも、ホーム画面に追加したPWAでも使える）
- GAS = 倉庫（JSONの受け口。マスタ・在庫・履歴の更新と取得）

```
iPhone（Safari / ホーム画面アプリ）
  └ 単一HTML：カメラ・ZXing-js・音・読み上げ・5つのモード
        │ fetch（GET＝読み取り、POST text/plain＝書き込み）
        ▼
  GAS Webアプリ /exec  ── 排他制御（LockService）
        ▼
  スプレッドシート（4シート）
     商品マスタ / 入出荷履歴 / 検品履歴 / 棚卸履歴
```

## 2. 調べて分かったこと（設計に効いた事実）

| # | 事実 | 設計への影響 |
|---|---|---|
| 1 | getUserMediaはHTTPS（またはlocalhost）でしか動かない（MDN） | HTMLはHTTPSで配信する。LAN内のhttpではカメラが使えない |
| 2 | iOSのSafariは iOS 11 でgetUserMediaに対応（WebKit公式ブログ）。ホーム画面アプリ（standalone）では2019年のiOS 13で壊れ、iOS 13.4で直った（WebKit Bug 185448）。その後も報告は散発的 | ホーム画面アプリでカメラが動くかは**実機で確認が要る**。設定画面に「カメラ診断」を付け、動かない時の原因（HTTPSか、許可か、standaloneか）が分かるようにする |
| 3 | iOS Safariの BarcodeDetector は17以降も「既定で無効」（caniuse）。iOSのブラウザは全部WebKit | 読み取りは ZXing-js が必須 |
| 4 | ZXing-js（@zxing/library）は最新0.23.0（2026-04）。プロジェクトは「メンテナンスモード」。EAN-13/EAN-8/UPC-A/UPC-Eに対応。iOS 14.3以降はSafari以外のブラウザでもカメラが使える（同README） | 版を固定してCDNから読む。枠内の画像を自前でグレースケール化してZXingのコア（MultiFormatReader）に渡す |
| 5 | iOS Safariは Vibration API（navigator.vibrate）非対応（caniuse）。Androidは対応 | 「バイブ」はAndroidのみ。iPhoneは音・読み上げ・画面の点滅で知らせる |

| 7 | iOS 26からSafariの「ホーム画面に追加」はどのサイトもWebアプリとして開く（既定でオン）。ダイアログに「Webアプリとして開く」のスイッチがある（報道。WebKit一次情報は未確認） | 手順メモに「Webアプリとして開く」のオン／オフで挙動が変わると書く。オフ＝ブックマーク扱い＝Safariのブラウザ表示 |

| 9 | スマホから匿名でfetchするには、デプロイを「自分として実行／全員（匿名を含む）」にする必要がある | tokenで守る。デプロイの公開は利用者の操作 |

出典のURLは手順メモ末尾に載せる。

## 3. 画面の流れ

上部に5つのモード切替: **入荷／出荷／検品／棚卸／在庫**。カメラ表示と手入力欄は全モード共通（上部に固定）。歯車で設定。

### 共通
- 「カメラ開始」→ 背面カメラ → JANを検出 → 音（＋Androidはバイブ）＋画面の枠が緑に点滅
- 同じコードは約1.5秒は無視。別のコードはすぐ受け付ける
- 読めない時のために、JANの手入力欄と「写真から読む」を用意
- **マスタにないJAN**: その場で商品名・価格・ロケーションを入力する登録フォームが開く → 登録するとマスタに追加され、そのまま処理が続く（現在庫0で作る）
- ロケーションはどのモードでも商品の横に表示

### 入荷
読む → 商品名・価格・現在庫・ロケーションを表示 → 数量（−／＋／直接入力。＋10ボタンあり）→「入荷を確定」。
- ロケーション欄は変更できる。変えて確定すると、マスタのロケーションを更新し、履歴のメモに「ロケ変更: 旧→新」を残す
- 同じ商品をもう一度読むと数量が+1
- 確定後は「入荷 +3 → 在庫 13」と表示して次の読み取りへ

### 出荷
入荷と同じ流れ。ロケーションは表示のみ。数量が現在庫を超える場合は赤字で警告して確定不可（GAS側でも `insufficient_stock` で拒否。マイナス在庫を許すかは `CONFIG.ALLOW_NEGATIVE_STOCK`、既定は拒否）。

### 検品（照合専用。在庫は動かさない）
1. 検品名（伝票や便の名前）を入れ、**予定リスト**（`JAN,予定数` を1行1品。貼り付け）を用意する。「サンプルから予定を作る」で、マスタの全商品に同じ予定数を入れたリストを作って編集もできる
2. 開始後、スキャンするたびに該当行の実績が+1。行ごとに−／＋でも直せる
3. 予定と実績を並べて色で表示: **一致=緑／不足=橙／超過=赤／予定外（予定リストにない）=赤＋「予定外」**
4. 全商品が一致し予定外が無いと、上部に大きく「**検品OK**」（緑）。そうでなければ「差異あり」（橙）
5. 確定で「検品履歴」に保存（全行、差異つき）
6. 予定リストと途中経過は端末に保存され、画面を閉じても再開できる（シートは4枚の指定どおり。予定リスト用のシートは作らない）

### 棚卸
1. 棚卸名、**範囲**（すべて／ロケーションを指定）、**未カウント品の扱い**（そのまま／0とみなす）を選んで開始
2. 実物をスキャンして数える（+1ずつ。行ごとに−／＋、直接修正も可）
3. 画面に「帳簿在庫／実績／差異」を色つきで表示。未カウント品の一覧も見られる
4. 確定を押すと、まずサーバーで**差異のプレビュー**（書き込みなし）を出し、内容を確認して「確定」で反映
5. 確定すると、マスタの現在庫が実績に合い、差異分が入出荷履歴に区分=棚卸調整で残り、棚卸履歴に全行が残る

### 在庫確認
商品名／JAN／ロケーションで検索、ロケーションで絞り込み、並び替え（ロケーション順／商品名／在庫が少ない順／在庫が多い順）。合計の品数と点数を表示。行をタップすると商品名・価格・ロケーションを編集できる（**在庫数は編集不可**。在庫は入荷・出荷・棚卸でだけ動く）。カメラで読むと、そのJANで検索される。

### 設定
GAS WebアプリのURL／合言葉（token）、音・バイブ・読み上げのON/OFF、接続テスト（GETとPOSTを別々に）、**マスタの取り込み**（サンプルの貼り付けまたはファイル選択）、カメラ診断（HTTPS・standalone・許可状態・直近のエラー）。設定は端末のlocalStorageにだけ保存し、コードには何も書かない。

## 4. 4つのシートの列

スプレッドシート名: 「簡易WMS（商品マスタ・履歴）」。ドライブ「8_自作ツール・GAS」に置く。JAN列は文字列で保存（先頭の0を落とさない）。日時は日本時間 `yyyy/MM/dd HH:mm:ss`。

**① 商品マスタ**（1商品=1行。JANがキー）

| 列 | 見出し | 内容 |
|---|---|---|
| A | JAN | |
| B | 商品名 | |
| C | 価格 | 円。不明は空欄 |
| D | 現在庫 | 0以上の整数。**入荷・出荷・棚卸調整でだけ増減** |
| E | ロケーション | 棚番（自由入力。全角→半角、英字は大文字、前後の空白は除去して保存） |

**② 入出荷履歴**（追記のみ）

| 列 | 見出し | 内容 |
|---|---|---|
| A | 日時 | |
| B | JAN | |
| C | 商品名 | その時点の名前 |
| D | 区分 | 入荷／出荷／棚卸調整 |
| E | 数量 | 入荷・出荷は**正の数**。棚卸調整は**符号つきの差異**（実績−帳簿） |
| F | 処理後の在庫数 | |
| G | メモ | 例: `ロケ変更: A-01→B-02` / `検品:<検品名>` / `棚卸:<棚卸名>` / `初期登録` |

**③ 検品履歴**（追記のみ。確定時に全行を書く）

| 列 | 見出し | 内容 |
|---|---|---|
| A | 日時 | |
| B | 検品名 | |
| C | JAN | |
| D | 商品名 | |
| E | 予定数 | 予定外は0 |
| F | 実績数 | |
| G | 差異 | 実績−予定 |

**④ 棚卸履歴**（追記のみ。確定時に書く）

| 列 | 見出し | 内容 |
|---|---|---|
| A | 日時 | |
| B | 棚卸名 | |
| C | JAN | |
| D | 商品名 | |

## 5. 設計判断（提案を含む）

### 5-1. 検品と在庫反映の扱い（提案）
- **検品は在庫を動かさない**（照合専用）。確定では検品履歴にだけ書く
- 検品の確定を入荷として取り込みたい場合のために、確定後に「**この検品結果を入荷として取り込む**」ボタンを出す。別操作にして、押し忘れても検品履歴は残る
- 取り込みの中身: 実績数が1以上の商品を、**実績数（予定数ではない）**で入荷。予定外の商品も実物が届いているので含める。差異があっても取り込めるが、確認ダイアログに「不足N品・超過M品・予定外K品」を出す。マスタ未登録の商品は先に登録が必要
- 取り込んだ入荷は入出荷履歴のメモに `検品:<検品名>` を残す。**二重取り込み防止**: 同じメモの入荷が既にあれば `already_imported` で拒否する
- 将来の拡張案: 差異があるものだけ保留にして、承認後に取り込む（今回はやらない）

### 5-2. 棚卸の未カウント品の扱い（提案）
- 既定は**「そのまま」**（数えていない商品の在庫は変えない）。理由: 数え漏れで在庫が一斉に0になる事故を避ける
- 「0とみなす」は、**範囲を指定した棚卸**（ロケーション単位）で使う前提にする。範囲内で数えていない商品だけが0になり、範囲外は一切触らない。「すべて」の範囲で0とみなす場合は、対象件数を出して確認する
- 範囲外のロケーションの商品をスキャンした場合は、数えたものとして扱い、「範囲外ロケ」の印を出す
- 確定時の帳簿在庫は、**確定した瞬間のマスタの値**。数えている間に入出荷が動くとずれるため、棚卸中は入荷・出荷を止める運用にする（サーバーは止めない。制約として手順メモに書く）
- 棚卸履歴には、数えた商品と「0とみなした」商品を残す。「そのまま」にした未カウント品は残さない

### 5-3. ロケーションの持ち方（現行案と検討事項）
- **今回の持ち方（1商品=1ロケーション）**: マスタに棚番を1つ持つ。入荷時に確認・変更し、出荷・検品・棚卸でも表示する。在庫一覧で絞り込み・並び替えができる
- **ロケ別に在庫数を分けるべきかの判断材料**。次のどれかが起きたら分ける
  1. 同じ商品を複数の棚に置く（フリーロケーション、分散保管、ケース棚と小分け棚）
  2. ピッキング指示を出す（どの棚から何個取るか）
  3. 棚卸をロケ単位で厳密にやりたい（棚ごとに帳簿が要る）
  4. ロケ間の移動を記録したい
- **分ける場合の最小変更案**: シート⑤「ロケ在庫」（JAN／ロケーション／数量）を足す。商品マスタの現在庫は「ロケ在庫の合計」に変え、ロケーション列は「主ロケ」にする。入出荷履歴にロケーション列を足し、区分に「移動」を足す。今回のAPIは `location` を省略可能な引数として持たせてあるので、画面の変更が中心になる
- **ロケーションマスタ（棚番の一覧と存在チェック）は今回作らない**。自由入力＋正規化（全角→半角、英字は大文字、空白除去）で表記ゆれを減らす。タイプミスが多いようなら、一覧から選ぶ方式に変える

### 5-3b. 同じJANの別表記
ZXingはEAN-13のうち先頭が0のものを12桁（UPC-A）として返すことがある。照合は**先頭の0を除いた数字列（JANキー）**で行い、シートには入力された表記で保存する。チェックデジットは8・12・13桁で検証する。

### 5-4. マスタの取り込み（サンプルの流し込み）
- 書式: 1行1商品、`JAN,商品名[,価格[,現在庫[,ロケーション]]]`（カンマ・タブ・ダブルクォート対応、先頭の見出し行は自動で除外）
- 設定画面に貼り付けるか、ファイルを選ぶ。GASの `masterImport` に送って一括登録
- 同じJANが既にある場合は商品名・価格・ロケーションを更新（空欄の項目は更新しない）。**既存商品の現在庫は取り込みでは変えない**
- 新規商品に現在庫が付いている場合は、現在庫を設定し、入出荷履歴に「入荷／初期登録」を残す（履歴が必ず残る規則を守る）
- 応答は追加・更新・スキップの件数と、スキップした行の理由（JAN不正・商品名なし・重複）
- 検品の予定リストも同じサンプルから作れる（「サンプルから予定を作る」）

## 6. GASエンドポイント仕様

URLは1本（`/exec`）。応答はすべてJSON。成功: `{"ok":true,…}` / 失敗: `{"ok":false,"error":"<コード>","message":"<説明>"}`。

- 認証: `token` が スクリプトプロパティ `APP_TOKEN` と一致すること（`ping` だけ不要）。不一致は `unauthorized`
- 書き込みはLockServiceで直列化。取れなければ `busy`
- 数量は正の整数（1〜100000）。JANは数字のみ・8/12/13桁・チェックデジット有効

### doGet（読み取り）
| クエリ | 内容 |
|---|---|
| `?action=ping` | 疎通確認。`{"ok":true,"app":"simple-wms","version":"0.3.0"}` |
| `?action=masterGet&jan=…&token=…` | マスタ検索。`{"ok":true,"found":true,"item":{jan,name,price,stock,location}}` または `found:false` |
| `?action=masterList&token=…[&q=…][&location=…]` | 在庫一覧（商品マスタ全件。絞り込みは任意）。`{"ok":true,"items":[…],"count":N,"totalStock":M}` |

### doPost（本文はJSON。Content-Typeは `text/plain`。`action` と `token` を含める）
| action | 入力 | 動作と応答 |
|---|---|---|
| `ping` | なし | POSTの疎通確認 |
| `masterGet` / `masterList` | 上と同じ | 同じ |
| `masterUpsert` | `jan`, `name`, `price?`, `location?`, `stock?` | マスタに1件追加/更新。新規で `stock>0` のときだけ現在庫を設定して履歴に「入荷／初期登録」。既存商品の現在庫は変えない。応答は `item` |
| `masterImport` | `items:[{jan,name,price?,stock?,location?}]` または `text` | 一括取り込み。応答 `{added,updated,skipped,errors:[{line,jan,reason}],items?}` |
| `receive` | `jan`, `qty`, `location?`, `memo?` | 入荷。在庫を加算し、履歴に「入荷」。`location` が違えばマスタを更新しメモに「ロケ変更」。応答は `item`（更新後）と `history` |
| `ship` | `jan`, `qty`, `memo?` | 出荷。在庫を減算し、履歴に「出荷」。在庫不足は `insufficient_stock`（`stock` を返す） |
| `receiveBatch` | `key`, `items:[{jan,qty}]`, `memo?` | 検品取り込みなど。全件を検証してから一括で入荷。`key` が履歴メモに既にあれば `already_imported`。未登録JANがあれば `not_in_master`（何も書かない） |
| `inspectionSave` | `name`, `items:[{jan,planned,actual}]` | 検品履歴に全行を書く（在庫は動かさない）。応答 `{saved,matched,short,over,unplanned,allOk}` |
| `stocktakePreview` | `name`, `counts:[{jan,actual}]`, `uncounted:'keep'\|'zero'`, `scope?:{locations:[…]}` | 書き込みなしで差異を計算。応答 `{rows:[{jan,name,location,book,actual,diff,counted}],adjust:N,zeroed:M}` |
| `stocktakeSave` | previewと同じ | 差異を確定。マスタの現在庫を実績に合わせ、入出荷履歴に「棚卸調整」（差異が0でない行のみ）、棚卸履歴に全対象行を書く。応答はpreviewと同じ＋更新後の `items` |

エラーコード: `unauthorized` / `bad_request` / `invalid_jan` / `not_in_master` / `insufficient_stock` / `already_imported` / `busy` / `server_error`

## 7. 必要な設定項目

| 置き場所 | 項目 | 備考 |
|---|---|---|

## 12. v0.4（LOGILESS踏襲＋レコード方式）の差分と設計

要件の出どころ: ネタ帳「簡易WMS」ページの「要件定義: 簡易WMS（LOGILESS踏襲版）」「業務フロー詳細」「要件追加・訂正（2026-11-06）」「設計方針メモ: データの持ち方は『レコード方式』」。LOGILESS Developers の入荷予定伝票（`inbound_delivery`）の設計も参照した。1〜11章（v0.3）は、ここに書いた差分を除いて有効。

### 12-1. データの持ち方（今回の大きな変更）

- **予定・伝票ごとにシートを増やさない**。スプレッドシートはデータ置き場にして、**行（レコード）を追加していく**。**シートは9つで固定**し、増えるのは行だけ
- 入荷予定と出荷伝票は、LOGILESSと同じく「**ID＋状態を持つヘッダ**＋**明細行**」。明細行は予定数（数量）と検品済数を持つ。状態で絞り込める
- 参考にしたLOGILESSの設計: 入荷予定伝票は、ヘッダ（`status`・`finished_at` など）と明細行（`quantity`＝予定数、`received_quantity`＝検品済み数量、`status`）を持つ。取消は状態を `Cancel` にして完了日時を入れる（行は消さない）。LOGILESSのAPI本文には、検品に伴う状態の遷移は書かれていない（遷移は下の12-3で決めた）

### 12-3. 状態（ステータス）

**入荷予定（ヘッダの状態は、明細から毎回計算して保存する）**

| 状態 | 条件 |
|---|---|
| 入荷待ち | 検品済数も入荷済数も0（作った直後） |
| 検品中 | 検品済数 ＞ 入荷済数 の明細がある（スキャンして途中保存したが、まだ在庫に計上していない） |
| 一部入荷 | 入荷済数が1以上で、まだ残り（予定数に満たない明細）がある。**これが「入荷待ち」の持ち越し** |

**出荷伝票**

| 状態 | 条件 |
|---|---|
| 未検品 | 全明細の検品済数が0 |

| 検品済 | **全明細で 検品済数＝数量**。このとき検品履歴に全行を書き、検品日時を入れる。在庫は動かさない |
| 出荷済 | 出荷を確定した（明細の数量分だけ在庫が減る）。出荷日時を入れる |
| キャンセル | 取消（出荷済みは取り消せない） |

### 12-5. 業務フロー（v0.4）

**入荷（予定あり）**
1. 入荷モード「予定を消し込む」→「＋予定を作る」で予定名と明細（`SKUまたはJAN,予定数` を1行1品）を登録。ヘッダ（入荷予定）と明細（入荷予定明細）に1行ずつ増える。状態＝入荷待ち
2. 予定の一覧から選ぶ（絞り込みは状態）。商品をスキャンして**検品済数**を数える。行ごとにロケ変更（入力／ロケを読む）。中断する時は「途中保存」→ 状態「検品中」（在庫は動かない。別の端末からも続けられる）
3. 色: 検品済数＝予定数→一致（緑）／少ない→不足（橙。計上後は「一部入荷」で残る）／多い→超過（赤。計上可）／予定にない→予定外（赤）
4. 「計上して確定」→ 確認画面（商品ごとに 今回の入荷数・在庫 n→m・残）→ 確定で、**検品済数−入荷済数**を在庫に加算（入荷済数を更新、入出荷履歴に入荷、検品履歴にも記録）
5. 残りは「一部入荷」のまま次回へ。もう来ない分は「予定を閉じる（消込）」。入荷がまだ無い予定は「キャンセル」できる

**入荷（予定なし＝現物）**: スキャン→未登録JANはその場で登録→数量とロケ→確定→**確認画面（在庫 n→m）**→履歴（入荷）

**出荷検品＋送り状検品→出荷（伝票）**（改訂後の流れ: 伝票の用意 → ピッキング（任意）→ 送り状発行 → 出荷検品＋送り状検品 → 出荷確定）
1. 検品モードで伝票を用意: CSV取り込み、または1伝票を手入力。出荷伝票・出荷伝票明細に行が増える（状態＝未検品）。SKUは対応表でJANに変換する。**宛先などの個人情報は取り込まない**
2. ピッキング（任意）: 独立モードにはしない。検品画面の各行にロケーションが出るので、それを見て集める
3. 送り状発行: 配送業者側で発行する。発行された**送り状番号を伝票に記録**する（伝票ごとの「送り状」ボタンで入力／📷スキャン、または追跡番号CSVの一括取り込み）。記録先は出荷伝票シートの「送り状番号」「配送業者」
4. 出荷検品＋送り状検品: 検品モードで伝票を選ぶ（伝票番号のバーコードを読んで開始も可）→ 商品をスキャンして検品済数を数える → 荷物に貼った**送り状のバーコードを読み取る**（「送り状検品」欄。一致すると「一致」、別の伝票の送り状なら「不一致」）。途中保存すると「検品中」。**商品が全数一致し、送り状が一致すると「検品済」にできる**（サーバーが再確認。差異・不一致のうちは検品済にできない）
5. 出荷モードで「検品済」の伝票を選ぶ → 明細ごとの在庫 n→m（不足は赤）。送り状番号も表示 → 確認 → 確定で明細の数量分だけ在庫が減り、履歴（区分＝出荷、メモ＝伝票番号と送り状番号）、状態＝出荷済。在庫不足が1行でもあれば伝票全体を拒否（何も書かない）
6. 取り込み間違いの伝票は「キャンセル」できる（出荷済みを除く）。**検品済みのあとに送り状番号を変えると、検品をやり直しになる**（古い送り状で検品済みのまま出荷しないため）

**出庫**: スキャン→数量→**理由（必須）**→確認画面→確定。履歴は区分＝出庫、メモ＝「理由:…」

**棚移動**: スキャン→現在のロケ→移動先（入力／ロケを読む）→確認画面→確定。同じロケへは拒否

**実地棚卸**: ①開始 →②実在庫入力（スキャン／＋−／直接入力）→③確定（差異プレビュー→確定）。中止で入力を破棄。**棚卸中は他の在庫操作を止める（運用）**

**管理ビュー**: 入荷予定・出荷伝票の一覧（状態で絞り込み・明細の展開）、在庫の検索、入出荷履歴の検索（区分・キーワード）、CSVダウンロード

### 12-11. 送り状発行の提案（簡易WMSでの現実的な形）

**手本（送り状Chrome拡張。note記事より）**: Shopifyの未発送注文をAdmin APIで取得 → 配送方法名でキャリアを判定 → キャリアごとの取り込みCSV（ヤマトB2=42列、佐川e飛伝III=74列、ゆうプリR=105列、クリックポスト）を生成 → 各社ソフトで発行 → 追跡番号を取得（クリックポストは自動、他社は各社ソフトが出す追跡番号CSVを取り込み）→ Shopifyのフルフィルメントに登録。宛先（郵便番号・都道府県・住所・氏名）とお届け希望日時は、ブラウザ内で処理する。**拡張側に、番号を保存する独自のデータベースは無い**（記事に記載なし）。

| 案 | 中身 | 良い点 | 弱い点 |
|---|---|---|---|
| **発行案A（採用・実装済み）番号の記録と照合だけ** | 発行は配送業者側（既存の送り状拡張や各社ソフト）に任せる。WMSは、発行された**送り状番号を伝票に記録**し、出荷検品で**送り状もスキャンして照合**する。番号は伝票ごとの入力／📷スキャン、または追跡番号CSV（受注コード＋送り状番号）の取り込み | 宛先をWMSに持たない（個人情報を保存しない方針と両立）。キャリアのCSV仕様（列数・形式の変更）に追従しなくてよい。実装が小さい | 発行そのものはWMSの外。拡張とWMSの2か所を行き来する |

### 12-12b. 確定したスコープ・実機課題（ネタ帳の追記より）
- **在庫連携（在庫数をEC・モールへ同期）は対象外**。今回は倉庫内の在庫管理と出荷作業に閉じる。対応表は**SKU→JANの変換専用**（予備在庫・連携上限・割当率などの列は付けない）。出荷伝票の取り込み（EC→WMS）は対象内。出荷実績（送り状番号・出荷済み）のEC側への戻しは、在庫連携とは別の「出荷実績の戻し」として将来の論点のまま
- **実機課題: カメラがスムーズに動くか**。iOS Safariはピント合わせの制御が弱く、ZXing-jsの読み取り速度もネイティブに劣る。本家LOGILESSが専用スキャナ・ハンディ前提なのも同じ理由とみられる。実機確認では「連続スキャンのテンポ」「暗い場所・小さいJANでの読み取り」「ホーム画面アプリでの起動」を重点的に見る
- **ダメな場合の現実解**: Bluetoothバーコードスキャナ（リング型など）を足す。スキャナは**キーボードとして数字を入力して Enter を送る**ので、アプリ側は入力欄で受ければよい。**実装済み（v0.4.2・画面のみ。GASの変更なし）**: 設定の「スキャナ（キーボード入力）モード」をオンにすると、画面下のJAN入力欄にフォーカスを残し（画面のキーボードは出ない）、スキャナが送る「数字＋Enter」を読み取るたびに処理する。ロケ・伝票番号・送り状番号の読み取り待ちの時は、カメラを開始せず同じ入力欄で受ける。モーダル（確認画面・登録画面）が開いている間や、ほかの入力欄を使っている間はフォーカスを奪わない。**PCブラウザでの擬似キー入力（実キーイベント）までは確認済み。実際のBluetoothスキャナ・iPhone実機は未確認**。スキャナは「Enterを送る」設定が必要（読み取り後にEnterが無い機種は動かない）
